# 开发与审查共用编码标准

适用于本次人工编写或修改的代码。开发自查与独立 Review 共用此页，按下表只读涉及语言的参考。先复用已读且仍有效的项目约定。

## 判定依据

先核对运行版本、接口与兼容契约，再采用目标项目明确的规则和 formatter/linter 配置。项目没有规定的部分，采用相应语言参考；仍无明确要求时，保持模块一致性。文档与配置冲突时定位冲突并确认有效来源。外部指南的“强制”级别不自动成为项目门禁。

参考规则是 TP 采纳的维护性基线；涉及公开名称、序列化、数据库对象、错误或空值语义的调整须先核对调用者。历史不一致不授权顺手全文件格式化。生成代码优先检查生成源与既有生成约定。

## 从文件到代码块检查

开发自查与 Review 都检查完成后的代码呈现。先看文件结构，再沿阅读单元边界进入块内；发现一处紧凑表达式不代表格式维度已经检查完。

- 文件整体：辨认声明/导入、共享定义、业务入口及辅助实现的分组和顺序，相关内容是否便于定位。沿用项目组织方式；只有实际跳转、查找或修改困难时才建议移动代码，不强制排序、拆文件或增加分区标题。
- 相邻阅读单元：逐一观察本次范围内函数、映射语句、配置段、样式规则等独立块的开头与结尾，检查空行、缩进及一致分隔能否让边界容易辨认。相邻独立块连续挤在一起，即使块内语法清楚，也应单独评估其阅读影响。具体间隔遵循项目/语言约定；没有硬性约定时，可以提出有位置与理由的分隔建议，不把统一空行数量或“每个标签后空一行”当通用门禁。
- 块内细节：再核对表达式、字段/参数、条件、命名、注释及副作用。混合文件同时观察外层容器和内嵌语言，例如 Mapper 的映射块与 SQL、组件的模板与脚本；不要只检查内嵌语句而跳过外层组织。

用户指定整个文件时覆盖全文，包括首尾与所有同级块边界；只审查 Diff 时检查受影响块及必要相邻上下文，不扩展到无关历史代码。只读了片段、搜索命中或工具摘要时说明覆盖限制。汇总同类问题可给代表位置及影响范围，仍须检查其他相同边界；避免逐行重复意见或用一个笼统“格式紧凑”代替定位。

反馈中简短说明实际覆盖的文件组织、块间边界和块内内容，以及未覆盖处；复用现有审查/开发说明，不新增必填工件或固定审查轮次。格式化器只证明其实际规则与运行范围，命名、分组及阅读边界仍按实际呈现核对。

## 共同检查项

| 检查项 | 可行动的判据 | 取舍与例子 |
| --- | --- | --- |
| 格式与组织 | 按上述文件、相邻块和块内三个层次核对分组、分隔、缩进、换行、括号与导入；指出具体位置和适用依据 | 复用已安装工具的检查结果。未运行就说明静态核对；格式配置未规定的改进按实际阅读影响分级 |
| 命名 | 名称让调用者识别对象、动作及必要的单位/状态；同一概念一致 | `timeoutMs` 明确毫秒。短循环变量、Go 接收者等局部惯例可以保留；API 名称按兼容契约处理 |
| 必要注释 | 关键原因、外部约束、兼容取舍无法从代码得知时，就近解释；更新失效说明 | 临时 fallback 说明供应商限制和真实移除条件；不猜日期。显然的赋值和短函数无需逐句解释 |
| 接口说明 | 使用者需要知道但签名未表达的输入、返回、副作用、异常、资源所有权应有说明 | 复用已有接口文档、类型与语言 doc 注释；不强制每个私有函数都附模板 |
| 控制流 | 阅读者能跟踪主要路径、失败路径、状态改变和副作用 | 嵌套三元或连续链式变换藏了业务分支时建议展开；清楚的简单三元、推导式、惯用表达可保留 |
| 职责与抽象 | 解释某一动作所需的跳转和背景与问题复杂度相称；抽象有实际用途 | 混合业务决策、远程请求与事务时说明维护影响；不按统一行数/嵌套层数硬拆，也不为去重制造无实际调用的层级 |
| 错误与资源 | 失败后状态、异常传播、事务边界及资源释放责任可确认 | 找出实际吞错、漏释放或错误回退路径；既定兼容回退要保留行为，避免仅凭“不够严格”新增拒绝条件 |

读者基线是熟悉当前语言与基础框架、但未参与本任务的开发者能维护。定位具体理解障碍及其修改风险，而不是只说“难看”“太长”。新增/修改的人工注释默认中文，解释原因、约束或风险；项目已有对外文档语言约定时沿用该约定，技术术语保留原文。

## 结果分级

- 必须修复：本次变更违反项目明确采用且适用的要求，或有可证明的正确性、安全、兼容性、维护风险。格式违规可依据已采用配置提出，不因与功能无关就归为个人偏好。
- 建议修复：具体维护收益成立，但影响有限或存在合理取舍。指出位置、影响和保留行为的修改方向。
- 可选优化/无需修改：多种写法均符合约定，仅体现个人偏好；清楚的惯用写法、已解释的例外、范围外历史问题不阻塞本次交付。

沿用现有 Review 的范围、Finding 与正式记录规则。每个意见连接“有效依据 → 代码位置 → 违反情况或维护影响 → 最小改法”。缺少调用契约时先标明待核，不把假设写成缺陷，也不为未要求的行为提出修复。
