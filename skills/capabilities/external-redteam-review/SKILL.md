# 外部红队对抗审查

## 1. 适用场景与唯一触发前提

本能力用于用户发现当前开发 Agent 存在无依据防御、过度开发、方向错误或测试自证时，由用户在另一工具中引入外部独立 AI 对抗审查。

- **用户唯一触发**：只有 `human_owner` 明确指令要求红队介入时启用。主 Agent 不得自主启动，其他 SKILL、Task 创建/模式/等级/阶段/失败及普通用户纠错反馈均不构成触发。
- **外部独立性**：红队由用户指定的外部 AI 担任，当前开发 Agent 是被审方。严禁当前 Agent 自查或派发同宿主子 Agent 冒充外部红队。
- **红队只产出意见**：红队不编写代码、不修改产品、不替代开发修复；意见范围由当轮用户指令界定，不将意见扩张为新的实施授权。

## 2. 上下文交接与只读审查准则

被审方交接给外部红队的最低上下文包必须以用户原始意图为锚，包含：
1. **原始用户输入与已确认需求**：包括明确的约束、边界与非目标。
2. **审查对象当前状态**：冻结代码版本、文档路径、内容身份指纹（SHA-256）与必要调用契约。
3. **真实证据**：已有的真实运行日志或测试回执；未运行项保持未验，不提供无依据的自拟测试通过证明。

外部红队审查要点：
- 检查是否存在缺乏需求/现实缺陷依据的防御性代码、配置或 fallback。
- 检查是否存在单消费者抽象、重复造已有 helper 轮子或无承诺威胁的空想防御。
- 检查测试预期是否直接来源于需求，排除自拟规则、自写断言、自证正确的循环。
- 允许无问题（No findings）、证据不足或保持未定位，不设最低问题配额。

## 3. 被审方证据回应与纠正

开发方收到外部红队意见后，不得盲从亦不得虚意迎合：
- 逐项比对真实代码、需求与已有契约，明确表态：接受、部分接受、反驳、待提供证据或待用户决定。
- 接受意见后的纠正修改必须限制在当轮授权范围内；若意见涉及重大业务取舍、权限放宽或准入变更，必须交回 `human_owner` 决策。
- 明确反驳时须给出确切的技术依据、契约条款或反证数据；未证实疑点与确定缺陷严格区分。

## 4. 留痕协议与 CLI 记录规范

双方所有交互、原文、回应及证据均沿当前 Task 留痕，不新建额外账本或状态库：

1. **工件保全**：
   - 外部红队原始意见、被审方回应保存在 Task 的 `evidence/redteam/<轮次>/` 下（例如 `external-review-original.txt`、`developer-response.md`）。
   - 每轮建立 Markdown 证据索引文件（如 `exchange-001.md`），记录原件相对路径、实际 SHA-256、外部来源工具/模型声明（标明未独立验证）与实际转录角色。
2. **正式事件记录**：
   - 使用现行纯过程事实入口：
     ```bash
     tp-spec event add --task <TASK> --type FACT --actor tp-project-manager --note "<轮次摘要，包含索引SHA-256；非专业完成或PASS>" --evidence <索引相对路径> --db <DB>
     ```
   - 避免使用 `task checkpoint` 记录过程附注，防止产生非预期的阶段 `COMPLETED` 伪完成或 `development` 下强制捕获 `ChangeSet` 副作用。
   - 记录完毕后在批次收口时执行投影刷新，必须显式传入真实执行角色（如 `--actor tp-project-manager`），严禁缺省依赖默认值导致误记为 `human_owner`：
     ```bash
     tp-spec reconcile --task <TASK> --task-dir <TASK_DIR> --actor <真实执行角色，如 tp-project-manager> --db <DB>
     ```

## 5. 连续复核与收口准则

- 用户授权的一轮审查允许连续完成提出异议、回应/修改、红队复核。该轮结束后主 Agent 不得自行重启新一轮。
- 外部红队复核原文必须如实保全；开发方严禁代签红队通过。
- 收口区分：
  - **红队无实质异议**：经复核确认无剩余阻断意见。
  - **用户接受剩余问题**：用户明确接受已知风险并指示继续。
- 外部红队无实质异议不替代既有的 `ARCHITECTURE` / `CODE` 独立专业审查与真实测试验证义务。
